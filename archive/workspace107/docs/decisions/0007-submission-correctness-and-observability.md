# ADR-0007 提交路径的正确性与可观测性

状态：已接受 · 阶段：M1.5（M2 前置加固）· 相关：GR-002、GR-007、GR-015

## 背景

拿一份外部工程约束清单（另一个项目的 `docs/constraints/`）对照检查本仓库，
逐条 grep 验证之后，确认了四个真实缺口。它们的共同点是：
**M1 的功能都是对的，但都只在「一个用户、一次点击、数据量很小」的前提下成立。**

| 缺口 | 具体表现 |
| :--- | :--- |
| 并发 | 并发上限是「数一数 -> 创建」，两个请求会同时通过；重跑路径**完全没查**上限 |
| 幂等 | 提交 Run 没有任何去重，双击或重试就是两倍算力消耗 |
| 分页 | 所有列表返回裸数组，没有 total 也没有游标 |
| 可观测 | 没有 request_id、没有结构化日志、没有就绪探针 |

对一个按 GPU 时长记账的平台，前两条不是体验问题，是钱和权益正确性的问题。

## 决策

### 1. 并发上限靠锁权益行串行化

提交 Run 之前先对该 Workspace 在目标算力方案上的权益行做
`SELECT ... FOR UPDATE`，锁持有到本次请求事务结束。

```text
锁权益行 -> 数未结束的 Run -> 创建 -> 提交 -> 提交事务（释放锁）
```

第二个并发请求在第一步就被挡住，等第一个提交完再数，数出来的就是最新值。

**为什么不用唯一约束**：约束能表达「不能重复」，表达不了「最多 N 个」。

**为什么不用乐观锁**：乐观锁要在权益行上维护版本号并在冲突时重试。
重试意味着整个提交流程（含准备工作目录）要重跑，而这条路径上有副作用，
不是幂等的。悲观锁在这里更简单也更安全。

**已知限制**：SQLite 不支持 `FOR UPDATE`，SQLAlchemy 的方言会忽略它。
开发和测试环境依赖 SQLite 自身的写串行化，**严格保证只在 PostgreSQL 上成立**。
这一点写在代码注释和测试用例里，不指望别人自己想到。

### 2. 唯一约束冲突在仓储层翻译成领域错误

「先查重、再插入」在并发下必然有窗口，兜底靠数据库唯一约束。
但它抛的是 `sqlalchemy.exc.IntegrityError`，不翻译就是 500 加一串堆栈。

所有写入统一走一个 `_flush()`，按约束名把冲突翻译成 `ConflictError`（409）。

**为什么翻译放在仓储层**：`application/` 不允许 import sqlalchemy——
这条边界由 `test_layering.py` 强制。要在用例层处理，就得让用例认识 ORM 异常，
那等于把边界打穿。仓储本来就是「把存储细节转成领域语言」的地方。

匹配规则同时覆盖两种报错文本：PostgreSQL 带约束名，SQLite 只带表名和列名。

### 3. 幂等键必须在提交调度任务之前落库

```text
登记幂等键并 flush          <- 复合主键在这一刻就生效
        ↓
准备工作目录、创建 Run
        ↓
提交给调度系统              <- 到这一步才产生外部副作用
```

顺序反过来的话，并发的第二个请求会**先把作业提交出去**，
再因为键冲突回滚——数据库是干净的，但集群上多跑了一个没人认领的作业。
这类问题事后极难发现，因为平台侧没有任何记录。

**键按 Workspace 隔离**（复合主键 `(workspace_id, key)`）：
和其他对象一样落在 Workspace 边界内（GR-001），两个空间用同一个键字符串互不影响。

**重放返回 200，新建返回 201**，两者都在契约里声明。

**前端把「意图」和「点击」分开**：提交弹窗打开算一次意图，
之后点几次提交、失败重试都用同一个键；成功之后才换新键。
光靠禁用按钮挡不住网络层的重试，光靠幂等键挡不住用户真的想跑两次——
两者是不同的事，各自解决各自的。

### 4. 分页只给历史类列表

判断标准是**规模由什么决定**：

```text
历史类：随时间单调增长，用一天就多一批
→ Run、Project Version、Project —— 必须分页

状态类：由当前状态决定规模，删掉就少了
→ 项目文件、成员、变量、运行方案、算力方案 —— 返回数组
```

给文件树套分页只会让本来该一次看全的东西变难用；
给 Run 列表不分页则是等着某一天它把接口拖垮。测试里有一条专门守住这条规则。

**为什么现在做**：M2 要加活动流和通知中心，那是天然无界的列表。
等那时候再往 `RunOut[]` 外面套信封，所有已经在用它的地方都要跟着改——
而前端类型是从契约生成的，改动会一路传导。趁契约还只有 39 个路径时定下来最省。

**offset 分页而不是游标**：Run 列表和版本历史是「翻页浏览」，用户要看到页码和总数。
代价是新数据插到头部时翻页会有轻微错位，对这些列表可以接受。

M2 的活动流如果需要稳定的无限滚动，应当**新增一种明确命名的游标模型**，
而不是把这一种悄悄改掉——改掉的话所有在用它的地方都要跟着改。

### 5. request_id 贯穿响应与日志，两个探针分开

```text
用户截图里的 request_id -> 日志里同一个 request_id -> 这次请求做了什么
```

响应头 `X-Request-Id` 和错误响应体里是同一个值。上游网关传了就沿用，
方便跨服务串联。前端把它显示在错误提示里并支持复制。

探针分成两个：

```text
/health   进程活着吗。不检查依赖，不会因为数据库抖动而失败
/ready    依赖都通吗。数据库连不上返回 503
```

**为什么不合并**：编排系统用 liveness 决定重启、用 readiness 决定转流量。
合成一个的话，数据库短暂抖动会导致容器被反复重启，比不检查还糟。
容器 HEALTHCHECK 用 `/ready`，因为 compose 靠它决定什么时候放前端进来。

日志本地输出可读文本、生产输出 JSON。访问日志**只记路径不记 query**——
query 里可能带用户输入。

### 6. 大小限制分两层

```text
中间件：按 Content-Length 拦掉明显超大的请求，省掉先读进内存再说不行
用例层：单个文件的真实上限，因为 Content-Length 可能缺失或被伪造
```

上限从组合根注入而不是在用例里读全局配置——依赖写在构造函数上，
测试换一个小上限也不用改环境变量。

## 明确没做：接口限流

单实例可以在进程内做，多实例需要共享状态（Redis）。现在做等于给以后留一个
要推翻的实现。已记在 `deploy/README.md` 的「这里没有做什么」里，
不是忘了，是有意延后。

真要上的时候优先保护三条路径：登录、提交 Run、文件上传。

## 影响

- `RunService.create` / `rerun` 的返回类型从 `Run` 变成 `RunSubmission`
  （多一个 `created` 标记，用来区分新建和重放）
- 三个列表接口的响应形状变了，前端类型和调用点由契约生成自动传导
- 新增 `idempotency_keys` 表，需要一次迁移
- 新增两个不属于任何层的模块：`observability.py` 和 `domain/pagination.py`
  （前者是横切关注点，后者是查询的值对象）
- 幂等登记目前**只增不删**。数据量不大，但长期需要一个清理策略——
  留到 M2 的数据保留那部分一起做

## 验证方式

每条修复都验证过「撤掉之后测试会红」，不是写完就算：

| 修复 | 守住它的测试 |
| :--- | :--- |
| 重跑受并发上限约束 | `test_concurrency.py::test_重跑同样受并发上限约束` |
| 约束冲突返回 409 | `test_concurrency.py::test_版本序号撞车报_409_而不是_500` |
| 幂等重放不产生新 Run | `test_idempotency.py::test_相同幂等键只会真的跑一次` |
| 幂等键在提交前落库 | `test_idempotency.py::test_登记在提交调度任务之前落库` |
| 分页只给历史类列表 | `test_project_versions.py::test_状态类列表不分页` |
| request_id 前后一致 | `test_api_contract.py::test_错误体里的_request_id_和响应头一致` |
| 依赖不可用时返回 503 | `test_api_contract.py::test_数据库不可用时就绪探针返回_503` |

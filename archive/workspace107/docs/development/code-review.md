# 代码评审规范

## 一. PR 规模

一个 PR 只解决一个主要问题。可以包含：

```text
实现 + 对应测试 + 必要文档 + API Contract 更新
```

不要混合：

```text
新功能 + 无关目录重构 + 依赖大升级 + 全项目格式化
```

普通 PR 控制在大约 300~500 行人工修改以内。
`docs/api/openapi.json`、`uv.lock`、`package-lock.json` 等生成文件单独说明，
不计入主要评审规模。

任务未完成但想提前同步设计或接口时，直接开 **Draft PR**。
不要等所有代码写完才让其他成员第一次看到。

## 二. 评审顺序

Reviewer 按以下顺序检查，不要在第 7 条上花掉全部时间：

```text
1. 是否真正满足 Issue 的验收条件
2. 是否破坏现有行为
3. 模块边界是否正确
4. 是否有必要测试
5. 权限和输入校验是否完整
6. 是否泄露密钥或用户数据
7. 命名和可读性是否合理
```

## 三. 本项目特有的检查点

### 3.1 分层边界

依赖方向必须是：

```text
api → application → domain ports ← infrastructure
```

- `domain/` 不得 import `fastapi`、`sqlalchemy` 或任何 `infrastructure` 模块
- `application/` 只依赖 `domain` 中定义的 Port，不直接依赖具体适配器
- `api/` 不写业务规则，只做请求解析、鉴权入口和响应序列化

### 3.2 依赖注入与接口契约

见 [ADR-0006](../decisions/0006-dependency-injection-and-api-contract.md)。
这两条大部分由测试和 CI 兜底，评审时重点看机器查不出来的部分：

- 新增的能力是**用例服务**，还是又往 `Services` 容器里塞了端口？
- 用例的新依赖是不是先在 `domain/ports/` 里定义了协议，而不是直接 import 实现？
- 后端改了 DTO，PR 里有没有带上重新生成的 `openapi.json` 和 `schema.d.ts`？
- 契约有没有「说实话」：枚举写成枚举了吗，自由字典能不能换成明确的模型，
  可以不传的字段是不是标成了可选？
- 前端有没有出现手写的接口类型？所有类型都应当从 `schema.d.ts` 派生。

### 3.3 并发与幂等

改到写入路径时想清楚这三件事，它们在单用户单击的场景下都看不出问题：

- 有没有「先读后写」？读到的数在写之前会不会已经过期？
  （限额、计数、序号分配都属于这一类）
- 「先查重再插入」有没有唯一约束兜底？约束冲突会不会变成 500？
- 会不会产生**外部副作用**（提交作业、发通知、调第三方）？
  如果会，去重必须发生在副作用之前——回滚回滚不了已经发出去的东西。

新增会消耗算力或额度的接口时，考虑是否要支持 `Idempotency-Key`。

### 3.4 列表接口

新增列表接口时先判断规模由什么决定：

```text
随时间单调增长  -> 必须分页，用 PageOut 信封
由当前状态决定  -> 返回数组
```

不要发明第二种分页形状。理由见
[ADR-0007](../decisions/0007-submission-correctness-and-observability.md)。

### 3.5 领域不变量

改动涉及以下内容时，对照 [`docs/domain/invariants.md`](../domain/invariants.md) 检查：

| 场景 | 必查不变量 |
| :--- | :--- |
| 新增对象归属关系 | GR-001 Workspace 是基础归属边界 |
| 版本、快照类对象 | GR-003 可变对象与不可变版本必须分离 |
| Run 创建与提交 | GR-009 Run Snapshot 创建后不可修改 |
| Run 输入 | GR-011 输入默认只读 |
| Secret、Credential | GR-012 Credential 不得通过普通对象传播 |
| 列表、搜索、错误信息 | GR-013 无发现权限时对象视为不存在 |
| 删除与清理 | GR-016 删除不能重写历史事实 |

### 3.6 密钥

- Run Snapshot、日志、API 响应和前端页面都不得出现 Secret 明文
- 新增配置项必须同步更新 `.env.example`，且只写变量名和说明
- 看到疑似真实 Token 立刻在 PR 中标出并要求轮换，不要只让作者删掉那一行

### 3.7 动态平台事实

GPU 型号、分区、QoS、配额、SSH 策略、预装软件版本属于会变的事实。
代码里不要硬编码成常量，文档里不要写成固定结论。

## 四. 评审礼仪

- 区分「必须改」和「建议」：前者写 `must:`，后者写 `nit:`
- 指出问题时给出理由或替代方案，不只说「这里不好」
- 作者不同意时先在 PR 中讨论清楚，不要沉默地改或沉默地不改
- 两轮 Review 还没收敛的分歧，拉维护者做决定，不要无限拉长

# 0003. 比赛优先可见切片，并保持能力可由原 107 独立消费

- 状态：已接受
- 日期：2026-08-11

## 背景

Competition V1 的时间约束要求优先形成评委能够直接操作和观察的功能闭环。原 Roadmap 把 M0 至 M5 全部列为比赛前置要求，并把 USTC CAS、完整协作授权和生产化收口绑定在同一条顺序路径上；这会让集成与加固工作挤压可见功能交付。

项目同时需要控制未完成风险：Mock 执行不等于真实 107 验证，开发身份、Secret 存储、宿主机 Shell 和本地文件系统不能越过其受控演示边界。若完整 Workspace107 未能按比赛范围完成，已经实现的能力仍应能由原 107 系统复用，而不是只能随整套新前端和数据库一起替换。

## 选项

1. **继续按 M0 至 M5 顺序完成全部能力** —— 目标完整，但比赛期可见交付容易被 CAS、权限治理和生产化工作阻塞。
2. **建设通用插件框架后再交付能力** —— 表面上复用性最强，但当前没有 Host 契约和真实插件消费者，会提前引入注册、生命周期、ABI 和 UI 扩展复杂度。
3. **按可见垂直切片交付，并固定窄 HTTP 消费边界** —— 保留模块化单体，通过版本化 OpenAPI 子集和 Host Adapter 让原 107 消费已完成能力；对演示妥协逐项登记和限制环境。

## 决定

采用选项 3：

- Competition V1 优先连贯、评委可见、端到端可运行的能力切片，不要求先依次完成 M0 至 M5 的所有能力和生产化事项。
- 每项交付必须披露实际运行模式和证据范围；Mock / Fake 路径不得表述为真实 107 Git、Shared FS、Worker 或 Slurm 已验证。
- USTC CAS、更丰富的权限与安全管理体验及生产化加固可以逐项延后；现有服务端 Ownership、Membership、Role 和对象范围校验不得移除。
- 受控演示不得使用不安全存储中的真实 Secret，不得向不受信任用户开放宿主机 Shell，不得在共享环境接受可伪造身份，也不得暴露未受控文件系统范围。这些是支持环境和发布声明的边界，不是新的产品功能优先级。
- 已实现能力以 **independently consumable capability slice** 交付：原 107 通过有文档、带版本的 HTTP / OpenAPI 子集和窄 Host Adapter 消费，不导入内部 Python 代码、不直接访问或共享数据库表，也不依赖整套 Workspace107 前端。
- 继续采用模块化单体。当前只承诺 HTTP-adaptable；在 Host-driven integration probe 通过前，不宣称通用或 drop-in plugin compatibility，也不建设插件注册、安装、生命周期、第三方 ABI / SDK、Microfrontend 或通用事件总线。
- `docs/product/deferred.md` 同时登记未来设计延后项和已接受工程 / 代码妥协。登记不覆盖产品设计、API Contract 或 Active GR；普通缺陷、在途状态和长期架构决定仍分别进入 Issue、Journal 和 ADR。

## 后果

- 好：比赛资源直接服务于可演示的完整功能，而不是用里程碑顺序或生产化清单冒充进度。
- 好：未完成整套产品时，原 107 仍可通过稳定的机器边界消费已完成能力。
- 好：身份、Secret、Shell 和文件系统风险被限制在明确支持环境内，演示妥协不会静默升级为生产承诺。
- 坏：Competition V1 不再等价于 M0 至 M5 全部完成；每项声明都必须带能力范围和运行模式，不能只报一个总版本状态。
- 坏：Host Adapter 和原 107 集成探针仍需按具体能力实现；本决定本身不证明兼容性。
- 坏：逐项维护工程妥协登记增加少量治理成本。
- **反悔成本**：低至中。优先级可以通过 Roadmap 调整；已经形成的 HTTP 契约和 Host Adapter 若被外部消费，则需要按契约兼容规则演进。

## 重新评估的条件

- 原 107 提供稳定的插件生命周期、身份、UI 或数据契约，并出现至少两个需要共享机制的真实插件消费者；
- Host-driven integration probe 证明 HTTP 边界无法承载目标能力；
- Competition V1 转为共享或生产部署，受控演示的身份、Secret、Shell 或存储 containment 不再成立；
- 项目开始对外承诺完整 M1 至 M5、生产数据兼容或正式 USTC 集成。

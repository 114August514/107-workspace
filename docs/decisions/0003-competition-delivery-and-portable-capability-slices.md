# 0003. 比赛优先可见切片，并保持能力可由原 107 独立消费

- 状态：已接受
- 日期：2026-08-11

## 背景

比赛时间有限，应先交付评委能亲手操作、能直接看到结果的完整功能。原路线图把 M0 至 M5 全部列为比赛前置，并要求按顺序完成 USTC CAS、完整的协作权限管理和生产环境加固。这些对接和加固工作会挤压可演示功能的交付时间。

项目也必须控制未完成部分的风险。Mock 执行不能作为原 107 真实环境已经验证的证据。开发用身份、凭据存储、宿主机命令行和本地文件系统只能用于受控演示，不能超出各自的限制范围。如果完整的 Workspace107 没有在比赛范围内完成，原 107 仍应能调用已经完成的功能，而不必同时替换整套前端和数据库。

## 选项

1. **继续按 M0 至 M5 的顺序完成全部工作** —— 目标完整，但可演示功能容易被 USTC CAS、权限管理和生产环境加固阻塞。
2. **先建设通用插件框架，再交付功能** —— 看似最方便复用，但目前没有原 107 的真实对接约定，也没有真实的插件调用方。提前建设会增加插件登记、安装、生命周期管理和前端扩展等复杂度。
3. **按完整功能流程交付，并只开放少量、明确的 HTTP 接口** —— 保留模块化单体。原 107 通过有文档、带版本的接口和一层很薄的对接代码调用已完成功能；演示中的妥协逐项登记，并明确限制使用环境。

## 决定

采用选项 3：

- 比赛版本优先交付从用户操作到看到结果的完整功能。功能必须连贯、可见、可运行；不要求先按 M0 至 M5 的顺序完成全部工作，也不要求先完成所有生产环境事项。
- 每项交付都必须说明实际运行方式和证据范围。Mock 或 Fake 路径不得说成已经在原 107 的真实 Git、共享文件系统、后台任务进程或 Slurm 上得到验证。
- USTC CAS、更丰富的权限与安全管理、生产环境加固可以逐项延后。现有服务端对所有者、成员、角色和对象访问范围的检查必须保留。
- 受控演示仍有四条不可越过的边界：不得在不安全的存储中保存真实凭据；不得向不受信任的用户开放宿主机命令行；不得在共享环境中接受可伪造的身份；不得读写未受控制的文件系统范围。这些边界限制支持环境和对外声明，不是新的产品功能优先级。
- 已完成功能应能由原 107 调用。对外只开放少量、明确、有文档且带版本的 HTTP 接口，并可用 OpenAPI 描述。对接时使用一层很薄的代码，只负责转换用户身份、项目 ID 和资源配置引用。原 107 不需要导入 Workspace107 的内部 Python 代码，不直接访问或共享数据库表，也不依赖整套 Workspace107 前端。
- 继续采用模块化单体。HTTP 是选定的未来对接边界；每项功能的具体接口和一层很薄的对接代码仍需实现，兼容性仍需由原 107 发起真实对接测试来验证。在测试通过前，不建设通用插件框架，也不宣称这些功能是可以直接安装使用的插件。当前不提前建设插件登记、安装、生命周期管理、前端插件体系或通用事件总线。
- `docs/product/deferred.md` 继续登记未来的产品设计延后项和已经接受的工程或代码妥协。登记不能改变产品设计、接口契约或正在执行的治理规则。普通缺陷仍记入 Issue，在途状态仍记入 Journal，长期架构决定仍写入 ADR。

## 后果

- 好：比赛资源直接用于可演示的完整功能，而不是用里程碑顺序或生产环境清单冒充进度。
- 好：少量、明确的 HTTP 接口和一层很薄的对接代码实现后，原 107 可以调用对应功能，而不必替换整套前端和数据库。
- 好：身份、凭据、宿主机命令行和文件系统的风险被限制在明确的支持环境内，演示中的妥协不会悄悄变成生产环境承诺。
- 坏：比赛版本不再等于 M0 至 M5 全部完成。每项声明都必须说明功能范围和运行方式，不能只报告一个总版本状态。
- 坏：这层很薄的对接代码和由原 107 发起的真实对接测试，仍需按具体功能实现。本决定本身不证明兼容性，也不表示对接已经实现。
- 坏：逐项维护工程妥协登记会增加少量管理成本。
- **反悔成本**：低至中。可以通过调整路线图改变优先级；如果已有外部系统调用这些 HTTP 接口和对接代码，后续变化就必须遵守接口兼容规则。

## 重新评估的条件

- 原 107 提供稳定的插件安装与运行规则、身份、界面或数据约定，并出现至少两个确实需要共享机制的插件调用方；
- 由原 107 发起的真实对接测试证明 HTTP 接口无法承载目标功能；
- 比赛版本转为共享部署或生产部署，身份、凭据、宿主机命令行或文件系统不再满足受控演示的四条边界；
- 项目开始对外承诺完整的 M1 至 M5、生产数据兼容或正式的 USTC 集成。

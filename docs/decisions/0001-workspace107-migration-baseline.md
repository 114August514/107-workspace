# 0001. 以 workspace107 已实现部分替换活动开发基线

- 状态：已接受
- 日期：2026-08-01

## 背景

目标仓库在 `374aa9f` 上有一套后端实现，另一个 `workspace107` 仓库在
`293c8d8` 上形成了后端、前端、契约和容器编排。两套实现使用不同的开发数据库
结构、目录和领域编号，继续并行维护会让协作者无法判断哪套代码代表当前事实。

目标仓库工作区还存在一条未完成的 `transfer -> execution_data` 重构。它处于新旧
实现并存且测试失败的状态，无法作为可迁移的稳定成果。

根目录 `DESIGN-final.md` 与 `GitGuideline.md` 已被指定为合并后的权威材料。来源
仓库文档中的旧 `GR-001..017` 和旧 Milestone 含义不能继续充当活动规范。

## 选项

1. 继续目标仓库实现，逐项重写来源功能。可以保留原开发数据库，但需要长期维护两套
   语义映射，且短期内得不到已经实现的前端和完整协作闭环。
2. 把来源仓库作为子目录长期运行。迁移成本低，但仓库会保留两个活动应用、两套规范
   和两套工程入口。
3. 固定双方历史，以来源的已实现部分替换活动开发基线，再按现行设计适配。

## 决定

采用选项 3：

- 用带注释 tag `archive/pre-workspace107-migration-2026-08-01` 固定替换前的目标实现。
- 将 `workspace107@293c8d8` 的全部已跟踪文件原样归档到
  `archive/workspace107/`，供协作者审查和追溯。
- 将来源 backend、frontend 及必要工程能力迁入活动目录，但不迁入旧产品、领域、
  Milestone 和开发规范作为活动指导。
- 明确放弃未完成的 `transfer -> execution_data` 工作区改动；只保留 journal 记录。
- 以根目录 `DESIGN-final.md` 的术语、规则和 Roadmap 适配代码引用与说明。
- 用跨平台 Python 任务实现统一开发命令；Makefile 只做薄转发，平台脚本只留在边缘。

这次替换发生在尚未形成数据保留承诺的开发阶段。来源 Alembic 历史成为新的活动开发
schema，不提供从 `374aa9f` 开发数据库原地升级的迁移链。仓库不会自动删除已有
`backend/var/`；需要旧数据时应固定旧 tag 读取，不需要时由开发者显式创建新数据库。

## 后果

- 好：协作者只有一套活动代码、设计基线和工程入口，同时仍能直接查看完整来源快照。
- 好：已实现的 Web/API 闭环、测试和部署材料可以在同一仓库继续演进。
- 坏：来源代码中的旧规则和阶段声明必须逐项校正，不能只做文件复制。
- 坏：旧开发数据库与新活动迁移历史不兼容，迁移前后的运行数据不能混用。
- 限制：当前 Mock 闭环不能证明现行 M1。真实 Git、Shared FS、独立 Worker、
  Apptainer 和 Slurm 路径仍需单独实现和验收。
- **反悔成本**：中。活动实现可以通过 tag 和归档恢复，但之后的新提交需要重新移植。

## 重新评估的条件

- 项目开始承诺共享演示或生产数据兼容，需要制定正式的数据迁移与回滚策略。
- 真实 Walking Skeleton 的验证表明当前 Scheduler/Storage 端口无法承载目标拓扑。
- 归档内容进入独立、可长期访问的版本库，才可以讨论从主仓库移除快照。

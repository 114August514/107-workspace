# 用户界面文案与反馈规范

本文是 107 Workspace 用户可见文案、状态反馈和操作提示的唯一权威入口。
领域对象及规则仍以 [`design.md`](design.md) 为准；本文只规定这些语义如何呈现在界面中，
不改变 API、权限或状态模型。

## 一. 基本语气

界面文案保持：**简洁、中性、明确、技术上准确。**

- 从用户正在完成的任务出发，不描述内部模块如何实现；
- 使用主动语态和具体动词；
- 标题、标签和说明各自只承担一个职责；
- 不使用“Oops”“太棒了”“空空如也”等拟人化、娱乐化表达；
- 不用感叹号制造紧迫感；真正需要注意的风险由内容和视觉层级表达。

## 二. 产品术语

同一概念在所有页面使用同一写法。代码、API 和诊断信息可以保留英文标识，普通用户文案
优先使用下表中的界面名称。

| 领域名称                | 界面名称                           | 使用说明                                            |
| :---------------------- | :--------------------------------- | :-------------------------------------------------- |
| User                    | 用户                               | 用户名、账号名保持原值，不翻译                      |
| User Group              | User Group                         | 目标产品中的协作与 Ownership 边界，保留英文         |
| Workspace               | 不新增                             | 旧实现和路由术语；新界面随产品语义迁移到 User Group |
| Project                 | Project                            | 保留英文                                            |
| Project Version         | Project 版本；局部上下文可写“版本” | 不写“代码快照”，除非解释版本语义                    |
| Run Configuration       | 运行方案                           | 不向普通用户暴露内部配置对象名                      |
| Run                     | Run                                | 保留英文                                            |
| Run Snapshot            | 运行快照                           | 只在复现、审计等需要解释固定内容的表面出现          |
| Environment             | 运行环境                           | 不简称“环境”，避免与部署环境混淆                    |
| Environment Version     | 环境版本                           | 在运行环境详情内可简称“版本”                        |
| Shared Resource         | 共享资源                           | 不显示 `SharedResource` 或简称 `SR`                 |
| Shared Resource Version | 资源版本                           | 在共享资源详情内可简称“版本”                        |
| Artifact                | 运行产物                           | 诊断或管理员表面可附带英文 `Artifact`               |
| Input Binding           | 运行输入                           | 不显示 `InputBinding`                               |
| Variable                | Variable                           | 保留产品正式英文名称                                |
| Secret                  | Secret                             | 保留产品正式英文名称，不展示明文值                  |

规则：

1. 页面标题已经给出对象时，空态和说明不重复完整对象名；
2. 对象名称使用中文引号，例如“imagenet-subset”；
3. 不把 API 类型名、数据库字段名或规则编号当作用户术语；
4. 管理员诊断表面需要展示英文原名时，将其作为次级信息，不替换主要文案。

## 三. 标题、按钮和辅助说明

### 3.1 标题

- 页面标题使用对象或任务名称：`共享资源`、`Run #13`、`发布资源版本`；
- 区块标题使用名词：`文件`、`版本`、`运行产物`；
- 标题末尾不加句号；
- 不用“管理”“操作”等宽泛标题替代具体对象。

### 3.2 按钮

按钮优先使用“动作 + 对象”：

```text
创建 Project
创建共享资源
发布版本
提交 Run
取消 Run
下载文件
保存修改
```

仅当当前上下文已经唯一确定对象时，才可省略对象，例如编辑共享资源弹窗中的“保存修改”。
避免把“确定”“提交”“处理”“下一步”作为没有具体含义的主操作。

### 3.3 辅助说明

辅助说明解释用户需要知道的条件、结果或下一步，不复述按钮文字，也不描述控件坐标。

禁止：

```text
点击右上角“发布新版本”
从左侧菜单进入
在下方选择文件
```

推荐：

```text
发布首个版本后，Project 才能引用这个共享资源。
```

物理位置会随窄屏和布局调整变化；操作入口由按钮和可访问名称说明。

## 四. 状态与反馈

### 4.1 Loading

描述正在执行的动作，不使用无上下文的“加载中”“处理中”或“请稍候”。

```text
正在加载共享资源…
正在读取文件…
正在发布版本…
正在提交 Run…
```

同一操作只显示一个主要 loading 反馈，提交期间禁用重复触发入口。

### 4.2 Empty

空态首先说明当前状态；只有用户具备对应能力时，才解释可执行的下一步并提供操作入口。

有创建权限：

```text
这里还没有共享资源。
创建共享资源后，可以在多个 Project 中复用同一份版本化内容。

[创建共享资源]
```

没有创建权限：

```text
这里还没有共享资源。
```

资源没有版本且可以发布：

```text
这个共享资源还没有已发布版本。
发布首个版本后，Project 才能引用这个共享资源。

[发布版本]
```

空态不得引导用户执行当前不可见或无权执行的操作。

### 4.3 Error

主要错误写“问题 + 下一步”。不把后端 message、HTTP 状态或异常类型直接作为主要提示。

```text
文件预览失败。
请检查网络连接后重试。
```

```text
无法发布这个版本。
请修正文件问题后重试。
```

请求标识等诊断信息可以次级展示：

```text
请求标识：req_01HZX…
```

有结构化错误码时按错误码映射用户文案，不匹配可能变化的 message 字符串。未知错误应明确
失败的动作并允许重试，不伪造原因。

### 4.4 Success

成功反馈说明已经产生的结果：

```text
共享资源已创建
版本已发布
Project 已创建
Run 已提交
```

避免“操作成功”。同一结果只反馈一次；Modal 关闭、页面刷新和 Toast 不应重复表达相同成功。

### 4.5 Permission

权限不足文案说明不能完成的动作；只有后端或稳定权限契约明确原因时才解释原因。

```text
无法发布这个版本。
你当前没有发布共享资源版本的权限。
```

未知具体原因时：

```text
无法查看这个共享资源。
请确认你仍有访问权限。
```

不要向没有操作能力的用户展示空态 CTA，也不要把角色名、Grant、内部规则编号作为唯一解释。
前端收敛入口只改善体验，后端仍逐请求校验权限。

### 4.6 Destructive

危险或不可逆操作必须明确对象、影响和结果；确认按钮重复具体动作。

```text
删除 Project“mnist-train”？
删除后，其当前文件、版本、分支、运行方案、Run 和从属运行产物将一并删除。
由该 Project 派生的其他 Project 和已经发布的独立资源不会受到影响。

[取消] [删除 Project]
```

后果必须来自当前产品规则。无法准确说明影响时，不得用模糊的“此操作不可撤销”代替调查。

## 五. 格式

### 5.1 时间与时长

- 绝对时间使用 `YYYY-MM-DD HH:mm:ss`；缺少值显示 `—`；
- “3 分钟前”等相对时间只用于快速浏览，并提供或可访问绝对时间；
- 跨时区或调度诊断表面明确显示时区；
- 时长使用自然单位，例如 `2 小时 15 分钟`，不写 `02:15:00` 代替普通用户说明。

### 5.2 容量与算力

- 文件容量使用 `B / KB / MB / GB / TB`，按 1024 进位；
- 算力使用现有产品单位，例如 `4 核`、`16 GB`、`2 张 GPU`；
- 数值和单位之间保留空格，中文量词除外；
- 不在前端文案中硬编码 GPU 型号、Partition、QoS 或配额事实。

### 5.3 ID 与版本

- ID、文件路径、命令和请求标识使用等宽样式；
- 可以视觉截断长 ID，但复制值和可访问名称必须保留完整内容；
- 版本显示后端提供的稳定标签，例如 `v3`；不自行发明 `latest`、`current` 等可漂移名称；
- 不把内部数据库自增键或原始字段名暴露为主要内容。

## 六. 禁止项

普通用户文案禁止直接暴露：

```text
multipart / FormData
HTTP 403 / 409
GR-401 等内部规则编号
数据库表名和字段名
Python / JavaScript 异常类型
slurmrestd 协议细节
```

管理员或诊断表面确需展示时，先给用户可理解的结论，再在次级区域展示技术细节。

同时禁止：

- 依赖页面物理位置的说明；
- 没有对象的“操作成功”“操作失败”；
- 没有下一步的错误；
- 对无权限用户展示不可执行 CTA；
- 为显得友好而牺牲技术准确性；
- 用文案掩盖缺失的 loading、empty、error 或权限状态。

## 七. Review 检查

新增或迁移页面至少检查：

- [ ] 产品术语与本规范一致；
- [ ] 标题和按钮使用具体对象或动作；
- [ ] loading 描述实际动作；
- [ ] empty 根据能力决定是否显示 CTA；
- [ ] error 表达问题和下一步，诊断信息处于次级；
- [ ] success 说明结果且没有重复反馈；
- [ ] permission 不猜测原因、不泄露内部规则；
- [ ] destructive 明确对象和真实后果；
- [ ] 文案不依赖控件物理位置；
- [ ] 时间、容量、ID 和版本格式一致；
- [ ] 桌面和 375 px 窄屏使用相同语义。

可运行的 Primer 状态示例不属于本文档任务，由
[GitHub Issue #26](https://github.com/114August514/107-workspace/issues/26) 跟踪。
